# TICVAI — AI Authorship & Attribution Policy

**Version:** 1.0
**Scope:** All five repositories. Binding.
**Owner:** Architecture (Chinmay)

---

## 1. Position

AI assistance is permitted and expected across the codebase. What matters is not whether
a machine helped, but that **provenance is recorded, review is proportionate to risk, and
a named human owns every line that ships.**

This policy exists for four reasons, in order of weight:

| # | Reason |
|---|---|
| 1 | **Accountability.** Every commit has a human owner who understands it and answers for it in production |
| 2 | **Review calibration.** AI-assisted changes in sensitive areas warrant heavier scrutiny. That is only possible if provenance is visible |
| 3 | **IP and licensing.** Generated code can reproduce training-set patterns. TICVAI is a client engagement; provenance may be contractually relevant |
| 4 | **Learning.** Knowing where AI assistance produced defects improves how the team uses it |

It does **not** exist to discourage AI use or to create a second-class tier of code.

---

## 2. Attribution Mechanism — Commit Trailers, Not Inline Comments

**Provenance is recorded at commit level using git trailers. Inline `// generated by AI`
comments are prohibited in hand-maintained code.**

### 2.1 Why not inline comments

| Problem | Detail |
|---|---|
| **They rot immediately** | A function is refactored twice and the comment now describes code nobody generated. Stale provenance is worse than none — it is actively misleading |
| **Wrong granularity** | AI assistance is rarely whole-function. It is a suggestion accepted here, a signature completed there. A comment cannot express that honestly |
| **Not machine-readable** | You cannot query "which of last quarter's incidents touched AI-assisted code" from free-text comments |
| **They create a two-tier culture** | Marked code gets skimmed as "the AI's fault" or distrusted regardless of quality. Both are wrong. All committed code is the committer's code |
| **They leak into client deliverables** | Source shipped or reviewed by TICVAI carrying authorship annotations invites the wrong conversation |

Git already solves this. Trailers are structured, queryable, attached to the change rather
than the file, and survive refactoring because they describe history rather than state.

### 2.2 The trailers

```
feat(orders): add dual-authorisation to refund flow

Implements 2.12.3 — a cashier may refund up to the role threshold with a
second user naming themselves as audit control. Not supervisor escalation.

Refs: C04, 2.12.3, 2.12.4
Assisted-By: Claude (Anthropic) <ai@softlabs.example>
Reviewed-By: Chinmay Parab <chinmay@softlabs.example>
```

| Trailer | When | Meaning |
|---|---|---|
| `Assisted-By:` | AI materially contributed — generated a block, drafted a function, produced the structure | The human authored and owns it; AI helped |
| `Co-Authored-By:` | AI produced substantially the whole change and the human reviewed and adapted it | Joint authorship, human accountable |
| *(neither)* | AI used only for completion of a line, lookup, or explanation | Not material. Do not over-attribute |

**Do not attribute trivially.** Tab-completing a variable name is not assistance worth
recording. The test is: *would a reviewer want to know?*

### 2.3 Enforcement

`.gitmessage` template ships with the repos. A `commit-msg` hook validates trailer format
where present. CI does not block on absence — attribution is a professional obligation,
not something to be gamed.

## 3. The One Exception — Wholly Generated Files

Files generated by a tool and **never hand-edited** carry a header. This is standard
practice for codegen and does not rot, because the file is regenerated rather than
maintained.

```csharp
//------------------------------------------------------------------------------
// <auto-generated>
//     Generated from ticvai-contracts openapi/spine/identity.yaml v1.4.0
//     Generator: openapi-generator 7.x
//     DO NOT EDIT. Changes will be overwritten on regeneration.
// </auto-generated>
//------------------------------------------------------------------------------
```

Applies to: generated API clients, generated DTOs, generated permission enums, Terraform
provider schemas.

**Does not apply to** AI-assisted code that a human then maintains. That is hand-maintained
code and falls under §2.

## 4. Human Accountability — Non-Negotiable

> **The committer owns the code. Authorship does not transfer responsibility.**

Before committing AI-assisted code, the committer confirms all of:

- [ ] I understand every line, including error paths
- [ ] I can explain why this approach was chosen over alternatives
- [ ] I have verified any API, library or framework behaviour it relies on actually exists
- [ ] It conforms to `NOMENCLATURE.md` and `CODING_STANDARDS.md`
- [ ] Tests cover the behaviour, and I wrote or verified the assertions
- [ ] No secret, credential, tenant identifier or personal data is embedded
- [ ] It does not introduce a dependency that was not already approved

**"The AI wrote it" is never an acceptable explanation of a defect.** If a line cannot be
explained, it does not ship.

### 4.1 Specific hazard — invented APIs

Language models produce confident references to methods, parameters and configuration
options that do not exist. Every external API call, library method, framework feature and
configuration key in AI-assisted code must be verified against real documentation before
commit. This is the most common defect class and it is trivially preventable.

## 5. Elevated Review Areas

AI-assisted changes touching these require **a second reviewer with domain knowledge**,
regardless of change size.

| Area | Why | Reference |
|---|---|---|
| **Authorisation and permission resolution** | Deny-overrides-allow, seven-level hierarchy. A subtle error is a cross-venue data breach | Direction §3.1 |
| **Tenant scoping and RLS policies** | A missing `FORCE ROW LEVEL SECURITY` is invisible in review and catastrophic in production | Direction §3.3 |
| **Payment and gateway integration** | Real money; recovery paths matter more than the happy path | 12 Aug §12 |
| **Ledger posting and revenue recognition** | Append-only; corrections are entries, not edits | 12 Aug §6 |
| **Money arithmetic** | Scale varies by region (OMR 3dp, AED 2dp); allocation must not lose minor units | — |
| **Offline sync and conflict resolution** | Ordering and idempotency failures produce duplicate sales | 31 Jul |
| **Cryptography, tokens, session handling** | Never hand-roll; never accept generated crypto without review | — |
| **Database migrations** | Runs across every cell. Errors multiply by tenant count | — |
| **PII handling and erasure paths** | PDPL/GDPR obligations against an append-only ledger | Direction §3.3.13 |

For these areas, prefer AI assistance for **tests, documentation and review** over
generation of the implementation itself.

---

## 6. Prohibited

| Prohibited | Why |
|---|---|
| Committing AI-generated code the committer cannot explain | §4 |
| Pasting production data, secrets, credentials or guest PII into an AI tool | Data protection; client confidentiality |
| Pasting client-confidential documents into a non-approved tool | TICVAI engagement terms |
| AI-generated cryptographic implementations | Use vetted libraries. Always |
| Accepting a generated dependency without licence review | Supply chain and IP |
| Inline authorship comments in hand-maintained code | §2.1 |
| Using authorship as a defect excuse | §4 |

## 7. Documentation and Comments

Separate from provenance. Comments explain **why**, never **what** — and the reason is
sharper here than in most projects: much of this code encodes decisions taken in specific
meetings for specific reasons, and that context is unrecoverable from the code itself.

**Good:**

```csharp
// FORCE is essential: without it the table owner bypasses every policy, which
// makes data-layer enforcement decorative for exactly the role most likely to
// run an ad-hoc query.
```

```csharp
// Rejection rather than displacement: auto-terminating the existing session
// can orphan an open cart or an unclosed cash drawer, which is worse for the
// operator than a refused login. See Direction §3.1.3.
```

**Useless:**

```csharp
// Set the tenant id
tenantId = value;
```

### 7.1 Cite decisions, not just requirements

Where code implements a contested or non-obvious decision, cite it:

```csharp
// 2.12.3 — dual-authorisation, NOT supervisor escalation. A second user
// (cashier OR supervisor) names themselves as audit control.
```

```csharp
// Scale carried per instance: OMR is 3dp, AED is 2dp. A fixed decimal(18,2)
// silently truncates every Omani transaction and the ledger is append-only.
```

This is the highest-value commenting in the codebase. Six months on, nobody remembers why
refunds have two authorisation paths, and the requirement ID makes it recoverable.

## 8. Metrics

Tracked quarterly, at repository level, **never per individual**:

- Share of commits carrying `Assisted-By` or `Co-Authored-By`
- Defect rate in AI-assisted versus unassisted changes
- Elevated-review-area changes with AI assistance and their review depth
- Rework rate on AI-assisted changes

Purpose is calibration — where assistance helps and where it costs. **Not performance
management.** Any use of these figures to assess an individual invalidates the data,
because people will stop attributing honestly.

## 10. Summary

| | Rule |
|---|---|
| **Attribution** | Git trailers. Never inline comments in maintained code |
| **Generated files** | `DO NOT EDIT` header; never hand-edited |
| **Accountability** | The committer owns it. Always |
| **Verification** | Every external API reference verified against real documentation |
| **Sensitive areas** | Second reviewer with domain knowledge |
| **Comments** | Why, not what. Cite the decision, not only the requirement |
| **Metrics** | Repository level. Never individual |
| **Client** | Confirm engagement terms before it is asked |
