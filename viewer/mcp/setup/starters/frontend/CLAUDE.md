## Git, build, test and lint: inside the repository folder

- Run git, the package manager, the build, the tests and the linter **inside the repository's
  folder** (`cd ticvai-pos` first, or `git -C ticvai-pos ...`). This folder is not a git repository.
- Take the commands from **that repository's own** `README.md` and the `scripts` in its
  `package.json`, with the package manager its lock file belongs to. Do not carry a command over
  from another repository or from memory. If it has no lint, typecheck or test script, say so; do
  not invent one.
- **Commit only inside the repository folder.** ADAM's files (`CLAUDE.md`, `.claude/`,
  `project-bible/`, `.adam/`) are this workspace's and never go into a team repository.

## Where the screen comes from

**The screen spec comes from ADAM, not from local folders.** ADAM holds the screens, journeys and API
contracts at a release; `adam_pull` writes the ones a ticket links under `.adam/work/<ticket>/` in
this folder, and `adam_screen`, `adam_journey` and `adam_contract` answer the rest. **A wireframe frame
`adam_pull` writes there (`wireframe-<anchor>.html`), or `adam_file` saves, came through ADAM: it is the
design** (see "Building a screen to its wireframe" below). A screen description, wireframe, mock-up or spec
file found anywhere else - in a repository, in another clone, in a download - is not the spec, however
recent it looks. Where it disagrees with ADAM, ADAM wins: say so.

## Hard rules

- **The screen and its API calls come from ADAM:** build what the screen and the contract say, to the look of
  the wireframe frame ADAM wrote for it.
- Clients never compute permissions; they read `effectivePermissions` from the session.
- Ids created on a device are UUIDv7, the format the server mints; human codes people read or type
  (order numbers, ticket codes) are separate fields.
- Function components with hooks, named exports, no `any`.
- **Offline goes through one store.** In an app that works offline, a write the contract marks
  offline-capable goes through the repository's single offline store and outbox; no screen talks
  to SQLite or does its own sync (frontend-patterns 4.4). Use the one the app's repository has; if it
  has none and the ticket needs it, say so rather than writing one inside the ticket.
- **The API client is generated, not written.** Calls go through the client generated from the
  contracts. Where the app's repository does not have it yet, build against the contract's types as the
  contract names them and stub the calls; never hand-write a client. Writes send an
  `Idempotency-Key`, and an error - RFC 9457 problem details - is told apart by its problem `type`,
  never by the status or the text (api-conventions).

## Working a ticket (ADAM)

ADAM is connected for this folder. It holds the screens, journeys and contracts; OpenProject holds the tickets.
If ADAM's tools are missing, see the top of this file: say "open the workspace folder" and stop.

No ticket named? Do not ask for a number: `adam_board` with `only: "workable"` gives `startHere`, the first ticket
you can finish or its first open sub-task of yours. Start that one.

1. `adam_pull` the ticket with `dir` set to this folder - the workspace, where this file is, not the
   repository folder - so `.adam/` stays out of the team's repository. Read `.adam/work/<ticket>/README.md`,
   then only the linked files it lists. Ask ADAM (`adam_screen`, `adam_journey`, `adam_contract`)
   rather than guessing a name or a shape.
   **Read its Comments section too**, the newest last: a clarification or QA's reason for sending
   it back overrides the description where they differ - say so when it does.
   **Sub-tasks** in README.md are the work under the ticket, in order: pull the first open one of yours and work
   that, one at a time; work the ticket itself only when none of its open sub-tasks is yours. **Part of** names
   the ticket it belongs to.
   **You are always on the latest release.** ADAM serves the package at its latest release tag
   (r1, r2, …) and every pull is at it; there is no release to choose and nothing to re-pin. If
   README.md says **What changed since your previous pull (rA -> rB)**, tell the person in one line
   (`spec-diff.md` has the diffs) and build against the files as they are now.
   **Read "Change requests on this ticket" too**, near the top of README.md: follow a settled
   decision where it differs from the description, and wait on the part an open non-blocking request
   covers; a blocking one is "When the package is wrong", step 4.
2. Build exactly what the ticket and its linked artefacts describe, in the repository for the
   ticket's platform (the table above), following its existing structure. Nothing outside the ticket.
   A screen is built to look like the wireframe frame the pull wrote (`wireframe-<anchor>.html`), every
   state included: "Building a screen to its wireframe", below.
3. Add tests the way that repository already writes them. Its lint, typecheck and test commands
   (see "Git, build, test and lint") must pass, run inside its folder.
4. `adam_propose` the ticket: **Ready for QA**, 100% (see the statuses below; never Closed), and a 2-4 line comment on what was built and
   that the checks pass. Show the proposal and **wait for a yes** before `adam_apply`.

To see a teammate's work, ask ("what is Hrushikant working on?", "what's everyone doing?"):
`adam_team` answers, read-only, with their open and in-progress tickets and what they finished lately.

A ticket's commit holds the ticket's change, made in the repository folder. Where ADAM's files sit
inside a repository (the setup-on-a-clone case above), setup has listed them in
`.git/info/exclude`; they are still not part of any ticket, so never force-add them.

## Building a screen to its wireframe

`adam_pull` writes, for every screen a ticket touches, the wireframe frame its record names
(`wireframe.board`, e.g. `wireframes/P01 Guest Web.dc.html#web-007`) as `wireframe-<anchor>.html` in the
ticket folder: one self-contained file, styles and images inline, that opens offline in a browser and looks
as it does in the ADAM viewer. **That frame came through ADAM, and it is the design.** README.md's
"How <screen> must look" says its status (client-verified, review, approved), whether a designer drew it,
and the client-approved prototype and views where there is one. To get a frame on its own:
`adam_file` with `path` the record's `wireframe.board` and `key` the ticket.

- **A client-verified screen is built to look identical to its frame** and to the prototype view the
  README names: layout, components, copy, imagery, spacing and colour. Client-approved UI is fixed: where
  the prototype has a view, it wins for the look; a screen or part it lacks is built from the screen record
  and the frame. The screen record gives the behaviour and the bindings; the frame gives the look.
- **Every state** the screen lists (loading, error, the empty states, offline) is built as README.md's
  "Each state's look" says: the state's own frame where the pull wrote one (`wireframe-<anchor>.html`, e.g.
  the WEB-029 status card for guest web's error), else the pattern the approved prototype draws, which it
  names and describes; a design gap (on the left-out list) in the frame's visual language. Never a plain
  heading, a plain sentence and a plain button.
- **The theme is the app's, never your own.** Colours, fonts, radii and spacing come from the app's design
  tokens, which its app shell applies: the repository's `SETUP-SHELL-<APP>` ticket (one per repository from
  r9: SETUP-SHELL-GUEST-WEB, -GUEST-APP, -POS, -KIOSK, -EMPLOYEE-APP, -VENUE-MANAGEMENT, -WEB) builds the
  shell and loads the tokens file README.md's **Theme** line names: the guest apps' from their approved
  prototypes (`handoff/design-tokens/guest-web.yaml`, `guest-app.yaml`, applied per tenant from
  `getPublishedTenantConfig`'s theme), every other app the shared `screens/_design-tokens.yaml`. A screen
  reads the tokens; it never invents or hard-codes a colour, font, radius or shadow. If the shell is not built
  yet, say so and build against the tokens file's names. The starter's `packages/design-tokens` holds the
  shared tokens only, not a guest app's.
- **A generated frame** (README.md says the frame is the record rendered as boxes) gives the structure, not
  the look: build its regions in order in the app's design system, and say so in the comment.
- **A placeholder layout only when no frame was written** (README.md says why); say so in the comment.
- Files under `wireframes/incoming/` that a record names are **structure only, not the look**, unless
  README.md says one is a capture of the prototype view (then it is the same look as the frame). A wireframe,
  mock-up or screenshot from anywhere but ADAM is not the design.

This replaces the older rule that a wireframe is built from only when client-verified, with a placeholder
layout otherwise: where an older paragraph of this file says that, this section wins.

## When the package is wrong

If the contract, table, screen or journey you are building from contradicts itself, is wrong, or
lacks something the ticket needs, **do not settle it in code** - not even with a sensible guess.

1. `adam_changes` for the artefact: somebody may have raised it already. If so, name that CR.
2. Otherwise `adam_draft_change`: quote the conflicting passages in `evidence`, list the `options`,
   say which you would pick in `recommendation`, set `blocking` and the `ticket`. The intake goes
   with it: `source` is `developer` (the reference defaults to the ticket) unless the person says
   it came from minutes, a client answer, a design or an audit - then `sourceRef`, and for minutes
   `clientSignoff`; `triage` and `when` if known; other `artefacts` it touches; `contractImpact`
   (none, additive, breaking - breaking needs an `approver`); `effortPoints` if the estimate moves.
3. Show the draft and **wait for a yes** before `adam_raise_change`.
4. **A blocker is always a change request** (CHG-ADM-004): set `blocking: true`, and once it is filed,
   propose the ticket **On hold** with "Blocked by CR-<n>" (applied only after a yes). Never work around
   it and never build a guess. Then find the next ticket you can finish: `adam_board` with
   `only: "workable"` lists, in board order, the tickets no open blocking CR affects (a ticket's
   `blocked` column and the "Blocked by" section of its README.md name the CRs). Propose the first one,
   and say which CR holds back each ticket you skipped.

Before building against an artefact, check `adam_changes` for an accepted request on it: the
package may be about to change.

## Ticket statuses (OpenProject)

| Status | Use it when |
|---|---|
| **New** | Not started. Never set it yourself. |
| **In progress** | Work has started but is not finished - a build that stopped part-way, or tests still failing. |
| **Ready for QA** | Done on your side: built as the ticket and its contract describe, and the tests pass. **This is where finished work goes.** Say in the comment what QA should check. |
| **Closed** | Set by QA after testing. **Never propose it yourself**, even when everything passes: the person who built it is not the person who says it works. |
| **On hold** | Blocked on something outside this repository - a missing contract, an unanswered question, an open change request. Say what in the comment. |
| **Rejected** | Only when the person says the ticket will not be done. Never on your own. |

Pair the status with % done: In progress 10-90, Ready for QA 100, On hold unchanged.
If the live statuses have no QA status, stop and ask rather than choosing Closed.
These are the statuses on pms.softlabsgroup.in. `adam_propose` with only a ticket number lists
the live ones; if they differ from this table, use those.

`.adam/` is a local copy and is git-ignored. Never commit it.
