01 / What Adam is

A contract-first package that refuses to contradict itself.

Nine validators

Nothing merges that disagrees

A screen cannot call an operation that does not exist. An operation cannot name a table stored nowhere. A state model cannot anchor on a schema with no values. A flow cannot step through a screen that was deleted.

Four hops, no duplication

Nothing holds a copy of anything else's truth

A screen names an operation; the operation resolves against the contracts; the contract resolves against the schema; the schema resolves against the relationship graph.

Derived, not maintained

Every artefact is regenerated where it can be

The boards come from the screens, the schema reference from the contracts, the relationship graph from both. A hand-maintained copy is a copy that goes stale, and this package has been bitten by that three times.

02 / The journey — before the derivation

From a room full of requirements to a decision the package can hold.

Seven steps happen with people in the room. Each one leaves something behind that Adam can read — a parsed pack, a minute, an ADR, a signed verdict — so the next step starts from the record rather than from memory.

        04 / Reading it back

        Four layers, one switch

        Contracts sit near the middle deliberately: the API is the join between the outer two, and every other layer is drawn by resolving against it.

          And read by the assistant writing the code

          Sixteen tools over MCP answer from the same index the viewer draws: one screen with its operations and states, one flow with its branches, one table with its columns and migration, one ADR in full, or the file behind any of them.

          The package itself stays read-only from the bridge. One tool records that a work package is about an artefact; one saves a ticket and what it touches as local files; and a status, % done or comment reaches OpenProject only after the developer has seen the change and said yes.
