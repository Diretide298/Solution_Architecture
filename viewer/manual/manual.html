TICVAI Architecture Viewer

Team manual — how to read the delivery package

The TICVAI delivery package is 24 API contracts, 347 screen definitions with a wireframe each, 12 user journeys, 39 state models, a 16-event catalogue and a database of 230 tables — spread across a dozen folders and five file formats. The viewer is a local application that reads all of it and draws the links between them, so you can follow a database column back to the screen that displays it and forward to the migration that creates it. This manual explains every layer, every view, every sub-view and every control.

Before you start

Two things are worth knowing up front, because they explain most of what the viewer shows.

Everything is read, nothing is generated. The viewer parses the actual .yaml, .sql, .xlsx and .md files in the repository every time it starts. There is no database, no export step and no cached copy that can drift. If the viewer shows it, it is in a file someone committed.

It distinguishes what is declared from what is guessed. A relationship somebody wrote down and a relationship the viewer worked out from a naming convention are drawn differently — solid versus dashed — and counted separately. Anywhere the viewer has inferred something, it says so on screen. This matters: 327 of the 347 screen navigation blocks and 289 of the 352 database relationships are inferred, and treating those as settled fact is the main way to misread the package.

Nothing leaves your machine

The viewer is a local server that only reads files beneath the repository root. It makes no outbound network calls and writes nothing to disk.

1 · Running it

Node 18 or newer. One install, then one command.

First time

# from the repository root
cd viewer
npm install

Every time

npm start        # → http://localhost:4173

Open http://localhost:4173 in Chrome or Edge. Add --open to have it launch the browser for you. Stop the server with Ctrl+C.

Flags

FlagWhat it does
--port 4173Serve on a different port, if 4173 is taken.
--openLaunch your default browser once the index is built.
--dir contracts Index a different contract folder. Use --dir repos/ticvai-contracts/openapi to read the authoritative copy in the contracts repo rather than the delivered snapshot.

Moving around

Every diagram and every sheet pans the same way: drag anywhere to move it. Scroll to zoom on the canvas views. A drag of less than a few pixels still counts as a click, so cards and rows open normally — you do not have to be careful about it.

Canvas views have a Fit or Recenter button that frames everything again if you get lost.

The sidebar

The grouping buttons at the top change per layer, and the amber note appears wherever a count needs explaining. Press m to cycle through the groupings without reaching for the mouse.

Hover anything you do not recognise

The package is dense with vocabulary that is obvious to whoever wrote it and opaque to everyone else: spine, ambient, saleBoard, retryThenDeadLetter, posTerminal, "declared", "inferred", "reversal". Hover it and it explains itself.

Two sources feed the tips, and the delivery's own words always win over the viewer's:

SourceUsed for
The delivery's files Component kinds and regions from screens/_components.yaml; schema descriptions and why the schema is separate from the workbook; a consumer's purpose and idempotency key from events/; a guard from states/.
A built-in glossary The viewer's own vocabulary and the delivery terms defined in prose rather than in a field — tiers, edge kinds, triggers, failure policies, what "critical" means.
A tip that only restates the name is not an answer

handoff/tooltips.json ships 340 hover entries, and its own README states the rule they were written to: "a tip reading 'Derived from fnb.Menu' is the same failure wearing text". 203 of the 340 break that rule, including 202 of the 230 table tips, which say only Derived from access.AccessPoint. So the file's coverage table claiming 230 of 230 counts keys, not answers — 137 are substantive. The viewer detects a restated tip and falls back to the workbook's own storage reason rather than repeating the name back at you, and the audit reports the count as a warning.

Everything explainable is hoverable: the five layer buttons, every view tab, every toolbar toggle and graph scope, every component and region on a screen, the four screen states, an API call's trigger, a schema in the Backend sidebar, and every chip in the event catalogue. Where the library names a component but gives no description — 14 of its 46 entries are primitives like textField and toggle — the tip says so rather than showing an empty panel.

Shortcuts cross layers

A view shortcut for another layer takes you there. Press d for Data while you are in Frontend and the viewer switches to Backend and opens Data. You never have to change layer first.

Adding a layer

The Domain layer was added exactly this way when states/ and events/ arrived, and the Decisions layer the same way when docs/ was indexed: one entry in the LAYERS array in public/app.js plus a render function. Nothing else in the application hard-codes the list, so services — expected to arrive as their own layer — will cost the same.

4 · Contracts layer

24 contracts, 654 operations, 554 schemas and 2,935 resolved $ref links. Six views over the same material, from furthest out to closest in. Four of them are here, each with its own controls; Lineage has the next chapter to itself, and the audit is in chapter 13.

Graph — how the contracts depend on each other

A map of the reference graph, with five scopes on the toolbar. They are not five styles of the same picture — each answers a different question, and picking the wrong one is why a graph can look like spaghetti. It opens on Spine.

Scope 1 · Spine — the architecture, and what actually couples it

The picture the obvious view cannot draw

The Files scope below draws 24 contracts and 44 $ref links — and every single one of those links points at shared/common or shared/permissions. No contract $refs another. So it produces a two-pointed starburst that is true of everything and distinguishes nothing: the same defect handoff/schema-viewer-notes.md identifies for venue_id and principal_id in the Data view.

The contracts are not joined by $refs. They are joined by events. order.paid is published by orders and consumed by catalogue, finance, inventory, marketing and reporting. Until events/ arrived there was nothing to draw that from.

Position carries meaning here, so the force layout is switched off. Within each ring the order is settled by pulling contracts that exchange events next to each other, which keeps the arrows short; drag one and it stays where you put it. Dots are sized by operation count rather than by degree — in the Files scope a contract's degree is always zero, so every dot there is the same size and the label claiming otherwise was wrong.

The Shared $refs toggle adds the 44 links back. It is off by default for the same reason Ambient keys is off in the Data view: an edge true of every contract tells you nothing about any one of them.

Scope 2 · Files — the raw $ref graph

Worth opening for one question only: how heavily does this contract lean on common? A thick edge means a change there lands on it. For anything about how contracts relate to each other, use Spine.

Scope 3 · Schemas — what shapes already exist

Use this when you are about to define a new type — if something close already exists, it is one of the well-connected nodes here. This is the busiest scope, 537 nodes, so turn Labels off to read the shape, or select something and press l to narrow to its neighbourhood.

Scope 4 · Permissions — who is allowed to do what

Use this for an access review: pick a permission and see every contract whose operations require it. Pink nodes are permissions, coloured ones are contracts.

Scope 5 · Local — just this thing and its surroundings

The scope to reach for when the others are too much. Select anything — from the sidebar, from search, from a link in the Reader — and press l. It is the fastest way to answer "what is this connected to" without reading a whole map.

5 · Lineage

Which tables an operation actually touches. 654 operations, 165 tables, 22 services. Contracts layer, Lineage tab.

Why this view exists

Until the lineage arrived, the Contracts layer and the Backend layer were two unconnected universes. A contract operation knew its permission and its scope. A table knew its columns and its foreign keys. Nothing knew that validateAccess writes access.scan_event.

That link is not derivable from the contracts. x-ticvai-persistence marks which schemas become tables; it does not mark which operations touch them. So the viewer was right not to guess it, and wrong only in having nothing to show. The join had to arrive as data, and it did — from four places, read by lib/lineage.mjs.

SourceCarries
handoff/api-data-lineage.json 654 operations against the tables each reads and writes, its service, its read routing, its scope level, its permission and whether it works offline.
The workbook's Data lineage sheet The same join, stated again — and not the same data. It carries a routing the JSON export lost, and a stored procedure column the JSON has no field for.
The workbook's Where used sheet The reverse index: all 230 tables against the operations and screens that reach each. Its own subtitle is the reason to read it — what breaks if this table changes.
handoff/screen-index.json 347 screens against their board anchor, operations, services, tables, stored procedures and wave.
Two sources, and one of them is lossy

The JSON and the sheet agree wherever both speak — 0 disagreements across all 654 rows. But the export dropped the routing value on 399 operations that the sheet decides, leaving an empty string where the sheet says write. A viewer reading the JSON alone therefore reports 399 operations as having no routing decided when the workbook has decided every one of them. So the sheet is merged in, it wins on the fields the export lost, and a row filled from it carries a mark saying where the value came from. Any disagreement between the two would be reported rather than resolved silently; there are none.

The chain

wireframes/LINKAGE.md draws the whole thing in one line, and it is worth keeping in view because every hop is a different file: 

board anchor  ──►  screen definition  ──►  operations  ──►  service
                                          │
                                          ▼
                                    tables · stored procedure

Worked through, from the delivery's own example: P07 Staff Scanner.dc.html#scn-004 is SCN-004 Admitted, which calls validateAccess, which lives in AccessService, writes access.scan_event, reads six tables including access.admission_profile and access.blacklist, and is one of the stored procedures — access.sp_validate_and_record. Five files answer that sentence. This view is the middle three of them.

The screen end of the chain is thinner than the operation end, and the index says so rather than padding it: 155 of the 347 screens declare an operation, and 108 reach a table. The rest are screens with a purpose and no declared operation — real screens, not yet specified, returned as empty arrays rather than guesses. Chapter 7 lays that out by wave.

The three scopes

The same material three ways, on the toolbar. It opens on Operations. A filter box narrows all three at once, and it matches operation names, paths, services and table names — so typing a table name in the Operations scope gives you everything that touches it.

Scope 1 · Operations — grouped by contract

Each group header says n of m resolved for that contract, which is the fastest way to see whose lineage is thin. A table chip for a table the schema workbook does not list is drawn as unknown and refuses to navigate — it tells you why instead.

Scope 2 · Tables — the other direction

Each table with every operation that touches it, drawn as a bar: red for the operations that write it, green for the ones that read it, sorted busiest first. The busiest tables are the ones a schema change costs most to make, and that is not visible anywhere else in the viewer. orders.sales_order is the busiest: 13 operations touch it, 12 reading and 7 writing, across two services.

The prose and the sheet disagree here, and the sheet is checkable

handoff/services-and-procedures.md says "orders.sales_order is read by 23 operations across four services". The resolved lineage gives 13 operations across two. The prose was written before the sheet was; the view counts rows rather than repeating the sentence, and the argument the sentence was making — that a table this contested is the case for the outbox rather than direct writes — survives the smaller number.

Above the bars sits the scope of the claim, taken from the Where used sheet rather than from the lineage: of the 230 tables in the schema reference, 191 are reached by an operation and 51 by a screen. The other 39 are reached by nothing at all — written by a job, a migration or a trigger, or by nothing yet. Those 39 are listed by name underneath, so the absence is a list rather than a subtraction.

Scope 3 · Services — 22 of them

The services mirror the contract boundaries exactly, and handoff/services-and-procedures.md gives the reason: "The contract is already the service boundary; inventing a different one would create two maps of the same territory." The rule that makes it a boundary rather than a namespace is the next line: "A service owns its tables and no others."

So the view computes the exception rather than leaving it to the eye. A table two services both write is a boundary drawn in the wrong place — whichever service does not own it is reaching across one. There are two: ledger.journal_entry, written by LedgerService, OrderService and ShiftService, and inventory.movement, written by InventoryService and MaintenanceService. Not defects on their own, but both are questions worth asking before the code exists.

Ten stored procedures, eight of them on the sheet

The delivery argues for services over procedures at length — RLS with FORCE exists so that nothing bypasses it, and a definer-role procedure does — and lands on ten. The Data lineage sheet names 8 against an operation; its own footnote and services-and-procedures.md both say "the ten stored procedures". The other two are argued for in prose and marked against nothing, so the viewer shows eight and reports the difference rather than picking a number. Six of the eight are named by a screen in screen-index.json, and it is those six it can place on a screen.

318 resolve to no table, and that is mostly correct

336 of the 654 operations resolve — 299 derived from persistence markers, 37 projections mapped by hand. The other 318 carry "source": "unresolved". All four numbers are chips across the top of the view, next to each other, always.

The 318 are not a defect list

Most of them return a computed projection — OrderSummary, TicketStatus, MediaEntitlements — assembled across tables rather than persisted, and a projection has no persistence marker because there is nothing to mark. The rest are commands with no response body, health checks and the sync endpoints. services-and-procedures.md states this is the correct outcome, not a backlog. Read the number as the shape of an API that returns more views than it stores, not as 318 rows of work.

They are drawn rather than dropped for the same reason inferred relationships are drawn dashed everywhere else: a view that quietly showed 336 operations would read as "these are all the operations there are", which is the more misleading number. So each is dimmed, with a no table chip where the table list would be, and the No table toggle removes them. It is on by default, and switching it off visibly removes rows — a count that changes when you hide something is a count you can trust.

The same file states where the resolved half is weakest, and the view inherits the weakness: "an operation that reads a table only to check a permission or resolve a scope does not show it. The lineage is what an operation is about, not every row it touches." Row security means every scoped read also touches platform.scope_node, and only six of the 654 rows say so.

What the view checks

The lineage and the contracts are two independent statements about the same 654 operations, so where they disagree one of them is stale. The reader compares three fields on every row — permission, scope and offline capability — against the contract the viewer has already indexed, and reports any difference as lineage-contradicts-contract. The contract is the source of truth, so a finding means the lineage needs regenerating. There are currently none.

Five tables the workbook does not list

orders.b, marketing.consent, reporting.report_execution, queue.queue_entry and whitelabel.homepage_section. Four of them look like tables that exist in somebody's head and not yet in the workbook. orders.b does not look like a table name at all — it reads as a truncation artefact in the source file, though that is an observation rather than something the viewer can establish. Either way the viewer names all five rather than dropping the chips, and the chips refuse to navigate.

Routing and scope

Every row carries where its read is routed and which level of the hierarchy it is authorised at. All 654 now carry a routing, but only because two files were read rather than one:

RoutingOperationsStated byMeans
write399The sheetA write. It goes to the primary by definition. Every one of these is blank in the JSON.
replica192The JSONA read that may be served from a replica.
primary35The JSONMust hit the primary — either it writes, or it reads something it just wrote.
analytical28The JSONServed from the analytical store. Never on a transaction path.
Absent is not the same as undecided

The 399 blanks were never a decision nobody had taken; they were a decision the export lost. The distinction matters because "nobody has decided" and "routed to the primary" are different claims and only one of them is safe to build on — so the reader fills them from the sheet and marks the chip, rather than either defaulting them to replica or leaving 399 operations looking undecided. Hover a marked chip and it says where the value came from.

Scope is stated for all 654: venue 410, tenant 153, workstation 45, region 44, brand 2. A grant at a level inherits downward and never bubbles up, so the venue-scoped majority is the shape of the platform rather than an accident of the file. 109 operations are marked offline-capable. Of the 336 that resolve, all 336 read at least one table and 256 of them also write.

Apps — what actually gets built

Each card carries the app's runtime, the platforms it serves, whether it is offline-capable, a wave bar showing the delivery shape, the contracts it consumes (clickable) and a collapsible list of its routes (also clickable). The design boards are listed underneath.

Wireframes — a board per platform, a page per journey

wireframes/ holds twelve platform boards, each drawing every screen on its platform as one anchored frame, alongside a page per flow and a contents page per platform. They are framed live rather than screenshotted, so they scroll and respond exactly as they do standalone.

Nothing here is inferred. A wireframe is either named for exactly the thing it draws — flow-f01.html is flow F01, p04.html is platform P04 — or it is a platform board carrying one frame per screen, and the anchor is the screen id, so P04 Staff POS.dc.html#pos-002 is screen POS-002. Neither join is guessed: the first is the file name, the second is declared by the screen itself in wireframe.board. The two sides line up exactly: 347 screens, 360 wireframes — 347 frames across 12 boards, 5 flow pages and 8 platform pages — and every screen resolves. A screen with no frame, and a frame no screen claims, are both reported as findings.

One frame, lifted out of the board

A board is a single file holding every screen on its platform — 713KB at the largest. Framing the whole board and scrolling it to an anchor would show the right screen with dozens of others around it, so the viewer lifts that one <div id="web-002"> out and serves it as a document of its own at /frame?board=…&anchor=…. The frames carry all their styling inline, so nothing is lost by moving one. All 347 extract with balanced markup, and the largest board drops from 713KB to about 10KB per frame.

These are structure, not design

A frame shows what is on a screen and where, not what it will look like. The field names, enums, states and deny reasons on it are read off the package — contracts/, states/ and screens/ — so a frame is checkable against the definition rather than invented. Where a screen had no definition at all — 136 had none — the frame is derived from the contract operations that reach no screen, and the board header says so. Waves — what ships when

The number this view exists for

How the drawings attach

The previous chapter states the rule the viewer now follows; this is the history behind it, because the earlier account was wrong in a way worth recording.

8 · Domain layer

Two artefacts that check each other. states/ says which moves between statuses are legal; events/ says what crosses the outbox when one happens. Between them they answer a question the contracts cannot.

Why this layer exists

The contracts declare 38 status enums — OrderStatus, SeatStatus, ShiftStatus and so on. Every one of them says what states exist. Not one of them says which moves between those states are allowed. So nothing catches an order going from held to refunded without ever having been paid: the enum permits it, the business does not, and until states/ arrived no artefact said so.

All thirty-eight enums now have a model — thirty-nine machines in all, one of them anchored to a schema that is not an enum — covering 225 states and 299 transitions. Nothing is left unmodelled. What remains to act on is that one model, checked against nothing.

8.1 · States — the legal moves

One machine per entity, laid out left to right by longest path from an initial state. Unlike every other diagram in the viewer, direction is the whole point here: paid → refunded and refunded → paid are not the same claim, and one of them is a defect. So every transition carries an arrowhead, and the layout makes "forward" a direction on screen rather than something to work out.

Reading a machine

What you seeWhat it means
Entry stub — a short arrow into the left edge An initial state. A record may be created here. Usually one; occasionally several, where a record can be created already advanced.
Double rule down the right edge A terminal state. Nothing leaves. The check that every state can reach one is what catches a state that traps records.
offline under the name A terminal can enter this state with no network. Everything else needs the server. On a POS this is the difference between a sale that completes and one that cannot.
Solid blue arrow An operation in a contract causes this move. Its operationId is the label.
Dashed green arrow A timer or a background job causes it. Dashed because no operation in any contract produces it — there is nothing to call and nobody watching.
Amber arc, bowing out of the row A reversal: a transition that undoes an earlier one. Marked because reversals are where money and entitlements move backwards, and they carry different approval requirements.
✓ before a label The transition requires approval — a person with the right grant must authorise it.
A state outlined in red Unreachable from any initial state, unable to reach a terminal one, or not in the contract enum at all. Each is a finding, and each appears in the audit.
Why reversals bow out of the row

Reversals are excluded from the depth calculation that decides which column a state sits in. A refund reaching back from completed would otherwise drag the whole tail of the machine leftwards and the diagram would read as a tangle. They are still drawn — they just do not decide where anything sits.

The guard — hover a transition

A transition's guard is the condition that must hold for the move to be allowed, and it is the real reason the file is written down: stated here, it is not only in whoever wrote the handler. Hover any transition to read it. Only the one under the pointer shows its guard — selecting a state can make five transitions active at once, and five guards would land on top of each other.

Selecting a state

With nothing selected the pane describes the model as a whole — its owner, its initial and terminal states, which states are reachable offline, and the author's note. Order's note is the clearest statement of what this folder is for:

From states/order.yaml

The sidebar — and the list that matters

Switch the grouping to Contexts for the other reading: the sixteen bounded contexts and what they owe each other, counted as n↑ published and n↓ consumed. Reporting consumes nine events and publishes none; marketing seven. That asymmetry is the shape of the platform.

8.2 · Events — what crosses the outbox

platform.outbox has always existed and has always been correct: publication is atomic with the state change, so a crash cannot leave an event unpublished for a change that happened. What never existed was a description of what it carries — who publishes, who consumes, what the payload is, and what a consumer does with a duplicate. Without that, an event is a contract between two services that neither one wrote down.

Sixteen events, forty-three consumers, twenty-one of them critical. order.paid is the most consumed event in the platform: five consumers, three critical. A dead-lettered order.paid means a guest paid and holds nothing, so it pages rather than logs.

The two rules the catalogue enforces

RuleWhy
Every event has at least one consumer An event nobody consumes is a write nobody reads — either the consumer was never built, or the event should not be published.
Every consumer states its idempotency key Delivery is at-least-once. A consumer that cannot say what makes a delivery a duplicate will process one twice, and the second time will be a Saturday.

onFailure takes one of four values, and hovering it in the table explains each: retry, retryThenDeadLetter (the usual choice for anything critical), deadLetterImmediately and ignore.

Commands are deliberately absent

This catalogue is facts that have already happened — order.paid, not payOrder. A published event a consumer can refuse is a distributed transaction wearing a disguise. Ordering is guaranteed per aggregate, never globally: two orders may be processed in any order, two events about the same order may not.

Two findings, as issued

states/entitlement.yaml is anchored to something that is not an enum. It declares contract: access, enum: TicketStatus — and access.TicketStatus is an object describing a validated ticket (ticketId, isValid, entriesUsed) with no enum values at all. The command-line checker disagrees, and it is wrong

CONTRACTS = ROOT.parent / "ticvai" / "ticvai-contracts" / "openapi"

10 · Decisions layer

A fifth layer over docs/: 18 ADRs, 31 register documents holding 1,107 rows, and one spec that is not read but run.

Why a layer for prose

Every other layer reads a machine-readable artefact — contracts, YAML, a workbook, CSV — and can be checked mechanically. docs/ is prose, and prose is where the reasons live. The four layers before this one say what the platform is. None of them says why it is that and not something else.

Prose is not renderable as a graph and should not be forced into one, so this layer does three specific things rather than trying to be a documentation browser: it indexes the ADRs so a reference to ADR-0013 anywhere in the viewer resolves to a title and a decision rather than a file name; it pulls the tables out of the registers, so what the delivery counted sits beside what the viewer computes; and it executes the permission spec.

One view, four scopes on the toolbar — Decisions, Permissions, Gaps, Registers — and its own Audit, as every layer has.

Decisions — the ADRs

18 ADRs, all 18 Accepted, 3 of them amended after acceptance. Each card carries the decision itself — the text under ## Decision, not the context around it — its date, what it closes, what it withdraws or supersedes, and what it constrains. Click the title to open the file.

The case that misleads

ADR-0001 is Accepted and its split rule is superseded by ADR-0014. Its status line is one line making three statements — "Accepted — split rule superseded by ADR-0014; isolation claim amended 14 August 2026" — and in a list of statuses it reads as current. The part that matters is not current: cells are no longer split by jurisdiction, they are split by Tenant × Region, and jurisdiction is now a placement constraint on regions. Everything else in the ADR still stands.

So the viewer takes the first word as the verdict and the rest as the qualifier, and marks the badge partly superseded where the qualifier mentions supersession. It is the qualifier that is worth reading.

An ADR carrying an ## Amendment section is marked amended for the same reason: the accepted date is then not the date of what the ADR now says. Three do — ADR-0001, ADR-0013 and ADR-0014. A status the viewer does not recognise, or no status at all, is a finding rather than a blank badge, because whether a decision is binding cannot otherwise be told from the file.

Permission vectors — the spec, executed

docs/architecture/specs/permission-vectors.json opens with one line: NORMATIVE. A failing vector is a build failure. It is the largest security surface in the platform written down as data. Each vector is a set of grants, a query, and the verdict the platform must reach.

A viewer that listed them would be a worse version of the file. One that evaluates them checks that the rule as written actually produces the answers the spec claims — which is the one thing reading it cannot tell you. So the viewer resolves every vector.

The rule, as the viewer implements it

Scopes are a seven-level tree — Tenant → Brand → Region → Venue → Department → Sub-Department → Workstation — written as a path, t_ref.b_alpha.r_north.v_alpha1. A grant applies when its permission matches exactly or the grant is *, and its scope is the query scope or an ancestor of it. Then: 

any applicable DENY   → DENY
otherwise any ALLOW   → PERMIT
otherwise             → DENY

The middle clause is the one people get wrong. Deny does not merely win at equal depth. V10 grants ALLOW at the venue and DENY at the brand above it, asks at the venue, and the answer is DENY — so there is no "most specific wins" tie-break anywhere in this. The spec's own reasoning is that under most-specific-wins a tenant administrator's blanket deny can be silently overridden by a venue allow somebody added months earlier; under deny-overrides, a deny is a guarantee. And nothing bubbles upward: a grant at a workstation says nothing about the venue that contains it (V04).

VectorGrantsAsksVerdict, and why
V01 none ORDER_CREATE @ venue DENY — default deny. Absence is never permission.
V03 ALLOW @ tenant ORDER_CREATE @ workstation PERMIT — inheritance runs six levels down.
V04 ALLOW @ workstation ORDER_CREATE @ venue DENY — nothing bubbles up.
V10 ALLOW @ venue · DENY @ brand ORDER_CREATE @ venue DENY — the specific allow does not override the broader deny.
V12 ALLOW @ tenant · DENY * @ region ORDER_CREATE @ venue DENY — the wildcard applies to denies.

22 of 22 pass. The spec's table states 28 vectors; the machine-runnable file carries 22. The six left out depend on inputs the grant model does not carry — which cell the scope is in, which role the session selected, the session's workstation, an inactive node in the path, an expired grant. Two of those, the inactive node and the expiry, are recorded in the spec as gaps in the platform's own resolver. A vector that failed here would be an error in this layer's audit, in the file's own words.

Writing the resolver found a bug — in the viewer, not the spec

The first run reported V12 as PERMIT where the spec requires DENY. The spec was right. The viewer had a small helper that strips markdown emphasis off a table cell, and it was being applied to grant data on the way into the resolver — so *, which is a real value in a grant, was being deleted. The wildcard deny became a grant for a permission named nothing, stopped applying, and the tenant-level allow won.

The fix was to stop treating data as prose: the resolver reads grant fields as written, and the stripping helper is marked for prose only. It is worth stating plainly because it is the evidence that the harness does real work — a view that listed the vectors would have shown a wildcard deny and been silently wrong about it.

Gaps — the artefact audit

handoff/artefact-audit.md classifies 3,297 requirements by the kind of artefact each one needs, derived from the requirement text rather than from a checklist somewhere else. It is the only register in the viewer that measures absence. Everywhere else counts what is there.

15 artefact classes, 12 open, 1,612 requirements behind them, and 8 classes with nothing at all behind them: Report (347 requirements), Configuration (273), Audit (206), Notification (193), Integration (171), Validation rule (94), Retention/archive (89) and Performance/SLA (30). The Report line is the clearest: 52 reports are named by title and nothing lists them. There is a report definition engine — createReport, runReport, scheduleReport — which is the right shape; what cannot be shown is that any particular named report is covered, because nothing maps title to definition.

Each class is a bar, and bar length is the requirement count — red where there is nothing behind the class, amber where cover is partial, green where it is covered. Hover a name for the audit's verdict and what the package currently holds against it. Eight classes with nothing behind them is the layer's one standing warning, and it is counted by the delivery's own audit rather than by the viewer.

Registers

31 documents holding 1,107 rows of reference data, in five groups: registers (7), the handoff narratives (9), architecture (6), in-flight (5) and guides (4). Each card shows the document's lead paragraph, its file and its row count; clicking one opens the source in the Reader.

The tables are the register and the prose around them is the reason for it, so the viewer reads both and counts the rows. Prose has no node in the graph, which is why a document opens as source rather than as a diagram.

16 · Keeping it current

Edit a source file, save, and the open page updates itself.

The server watches contracts/, flows/, screens/, frontend/ and backend/ and re-indexes on save — including the .xlsx, so editing the schema reference in Excel updates the Data view. No refresh, no restart. The green dot beside the theme button means the watch is live.

17 · Known gaps

On disk but not shown, and why. None of these are bugs; each is a decision.

Not shownWhy
Whole-platform sitemap Entry and exit points are shown per screen and are clickable, but there is no navigation graph across a platform. Worth building only once more of the 327 inferred navigation blocks are confirmed — a guessed sitemap drawn authoritatively is worse than none.
Platforms with no screen files None left. P03, P06, P07 and P13 were the last four; they landed and took the count to 12 platforms and 347 screens. The sidebar note counts platforms from the deployment table rather than asserting a list, so it stays right as more arrive.
Row-security policies The viewer says a table is FORCED, not what the 16 policies actually permit.
Board-to-region mapping A design board is attached to a screen, not to the part of the board that screen is. Reading one exported design board as nine screens is still a manual job. The wireframe platform boards do not have this problem — each screen has its own anchor on the board, so the viewer frames exactly the right part.
An events graph of its own The Domain layer lists contexts; the drawing of them is the Contracts layer's Spine scope, because they are the same 24 nodes. There is no view where events rather than contracts are the nodes.

Two tool results to distrust

tools/check-frontend.py looks for the frontend repository as a sibling of the project root, but it is checked out at repos/ticvai-frontend. It therefore reports screens across apps that do not exist. They do exist; frontend/platform-deployment.md is correct.

tools/check-states.py has the same bug in the same family — line 36 points at a contracts directory that is not there, so it loads zero enums and every lookup fails. Both pass once repointed. Fix the path before acting on either one's output; chapter 8 has the detail.

18 · Troubleshooting

SymptomCause and fix
Page will not load The server is not running, or something else holds port 4173. Start it with npm start --port 4180 and open that port instead.
The green dot is grey The live connection dropped — usually the server was stopped or restarted. Reload the page.
Edits do not appear Check the file is under a watched folder and has a watched extension (.yaml, .yml, .xlsx, .md). Excel's lock files and temporary copies are deliberately ignored, so the workbook only reindexes once you actually save it.
A diagram is a hairball Press Fit or Recenter. On Data, drill into one schema rather than viewing all 230 tables. On Graph, use Local with something selected.
Numbers disagree with a spreadsheet You are probably reading a stale copy of the workbook. The viewer reads the newest copy and reports the older one in the Backend audit.
A table shows no relationships Check Inferred keys is on. If it is, the table's _id columns resolve to nothing — see "keys with no table" in the Links pane.
A screen shows no navigation All 347 screens have navigation, but 327 blocks are inferred and drawn as dashed pills under their own heading. Look below the operations list.

19 · Glossary

TermMeans
SpineA core contract the platform is built on — identity, orders, catalogue, tenancy and so on. 8 of them.
SatelliteA bounded capability that plugs into the spine — F&B, games, assets. 14 of them.
Sharedcommon.yaml and permissions.yaml, referenced by nearly everything.
ModuleA functional grouping declared as x-ticvai-module, used to organise both contracts and screens.
PlatformA coded surface — P01 Guest Web Storefront, P10 Partner Portal, and so on. Declared per contract, so a contract appears under every platform it names.
WaveDelivery phase. Screens and apps carry the wave they ship in.
Flow / journeyOne job a person came to do, traced across screens, with the branches that can derail it.
BranchA way a journey step can go wrong, with a severity from recoverable through to data loss.
The four statesLoading, empty, error and — where the platform is offline-capable — offline. Every screen must declare all that apply.
DeclaredWritten down by a person in a source file. Drawn solid.
InferredWorked out by the viewer from a naming convention. Drawn dashed, counted separately, switchable off.
DDLThe SQL in backend/ that creates tables. The strongest evidence available.
Storage-only tableA table with no contract schema behind it, by design — outbox, schema version, partition defaults. 21 of them.
Composite keyA foreign key over more than one column, here usually (id, level) — needed because a scope node is identified by both.
Row security FORCEDRow-level security that applies even to the table's owner, not merely enabled.
Not persistedA contract schema deliberately backed by no table — a request body, a response envelope, an enum. 168 of them.
Ambient keyA key to one of the four hub tables — venue, principal, subject, tenant. True of nearly every table and therefore saying nothing about any one of them. 163 of the 352 relationships. Hidden by default.
Child edgeThis row belongs to that row and has no meaning without it. Drawn heaviest of the three edge kinds.
State modelThe legal transitions for one status enum: which moves are allowed, what causes each, and what must be true first. In states/.
Initial / terminalA state a record may be created in / a state nothing leaves. Every state must be reachable from an initial one and able to reach a terminal one.
GuardThe condition that must hold for a transition to be allowed. Written down so it is not only in whoever wrote the handler.
ReversalA transition that undoes an earlier one. Marked because reversals are where money and entitlements move backwards, and they carry different approval requirements. 40 of the 299.
Offline-reachableA state a terminal can enter with no network. Everything else needs the server.
Domain eventA fact that has already happened, published through platform.outbox — order.paid, never payOrder. In events/.
AggregateWhat an event is about. Ordering is guaranteed within one instance of it and never globally.
Idempotency keyWhat makes a redelivery a duplicate. Required of every consumer, because delivery is at-least-once.
Critical consumerOne the business breaks without. A dead-lettered critical event is a page, not a dashboard. 21 of the 43.
ContextA bounded context — which is also what a contract is. The 16 that publish or consume events are where the real coupling between contracts lives.
WireframeA rendered drawing of one screen, flow or platform, generated from the screen definition. Structure only — what is on the screen and where, not what it will look like. In wireframes/.
Design boardAn exported UI/UX artboard covering a whole platform, drawn by a designer. In designs/.
