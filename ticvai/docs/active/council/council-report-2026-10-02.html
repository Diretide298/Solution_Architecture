Council verdict: a complete audit, and a change log with prevention rules

"I feel let's do a complete audit, not just for Block A. Then, for any changes ahead, we write a log and instructions, so we can avoid them going forward and have a better way to integrate them." (Chinmay, 2 October 2026)

The one thing to do first

Today, write known-issues-block-a.md and declare the freeze line, so Block A is stable for Monday. Then start the F8 re-audit at 12:30 on Monday 5 October.

The recommendation

Phase 0: before Monday, no AI.

  • Commit or discard any partial agent work.
  • Bring every cited source into git.
  • Write known-issues-block-a.md, organised by ticket.
  • Declare the freeze line: a ticket past "New" changes only through an ADAM change-request delta, as a comment plus an addendum ticket. Its body is never rewritten.

Phase 1: Monday after 12:30.

  • Run the F8 re-audit of Block A.
  • With scripts only, turn the 293 root issues and the 248 corrections into checks:
    • audience vs field;
    • a config read that needs a session;
    • an enum that differs between contract, screen and prototype;
    • an orphan control;
    • an operation with no contract behind it;
    • an unbound field.
  • Validate each check against the F1–F7 set.
  • Sweep all 16 apps in the order A, B, C, D. That is the complete audit count, at zero AI cost.

Phase 2: weeks 1–2.

  • Use AI on a sample of 20 screens per app, to find new classes of issue.
  • Finish the 7 process agents, in block order.
  • Review each app's contracts for meaning.
  • Collect the contract decisions and the 53 open questions into one client sign-off queue. Silence counts as acceptance after 5 working days.
  • Fix forward, block by block.

Change log: ticvai/changes/CHANGELOG.yaml.

  • One row per change: id, date, source, root class, what it cascaded to, blast radius, frozen tickets affected, decision owner, check_added (or "none possible" with the reason), and the release tag.
  • No row closes and no change merges without a check that fails before the fix and passes after.
  • The first rows are this week's churn.

Integration.

  • One decision register, owned by the lead.
  • No reversing a decision within 48 hours.
  • Nothing is announced until it is committed.
  • Every change request is triaged as a blocker, a fix-forward or a deferral.
  • Releases go out Tuesday and Friday, with no spec edits the day before.
  • After each release, a canary run pulls 5 tickets.
  • A daily 30-minute triage slot for the lead.

Where the council agrees

  • The audit is by root cause, and the checks sweep every screen for free.
  • AI is used only where scripts can't see.
  • Started tickets are frozen.
  • The F8 re-audit comes first.
  • A change-log row closes only when a check is linked.

Where it clashes

  • When to run the full audit. The council's answer: in full, but scripted first and then AI by block.
  • Sample size. 20 screens per app.
  • The 48-hour rule vs one register. Both.
  • Commercial extras. Parked.
  • The Executor's claim that C1–C15 isn't built is wrong, and was discarded.

Blind spots caught in review

  • A fix reaches a started ticket only as a change-request delta against the release tag.
  • Check each new check for false positives: 367 findings in the last audit were false.
  • Controls with no field, the theme load that needs sign-in, and the guest policy read are decisions, not checks.
  • Errors of meaning in the contracts, such as the cart audience and the loyalty read, need a review for meaning.
  • The client needs a sign-off queue with a default for silence.
  • Developers need a known-issues note and a way to escalate.
  • The lead is a single point of failure.
The Contrarian

A whole-package audit run by AI repeats the method that already hit the capacity cap. Counting findings is not de-duplicating them. Fixes will break started work unless there is a freeze line. The change log is not the product. The lead is a single point of failure. First: run F8, then write scripted checks for the three deterministic classes.

The First Principles Thinker

The package has no single place where a fact is decided, and the audit is a symptom of that. The findings are 30–50 rule violations multiplied by the generator. Work rule-first: deterministic checks over all screens, AI only to find new classes. The log requires a link to a check. Churn needs one register and one owner.

The Expansionist

The root-cause catalogue is the deliverable. Make an unbacked control a hard error in the generator. The change log is a data asset that predicts blast radius and prices change requests. Run the meeting-input loop in reverse as sign-off evidence. Simulation before go-live uses the same machinery.

The Outsider

The audit is not the bottleneck; what happens to the findings is. Define what "done" means, and set a severity bar. The churn is a process signal: no decision reversed within 48 hours, nothing announced before it is committed. The log needs one required field: the check. Jargon makes it unreadable to newcomers.

The Executor

Monday is not about the audit. Run F8 on Block A and freeze. Audit by root cause through the merge-gate checks. Use AI only for the 7 process agents after the reset, in block order. One log file, and no row closes without its check.

Peer review highlights

Two reviewers ranked the Contrarian's response strongest and three ranked First Principles. All five flagged the Executor's response for its wrong claim about C1–C15. All the reviewers raised the same missing pieces:

  • an addendum path for frozen tickets;
  • validating each check against F1–F7;
  • contract semantics;
  • a client sign-off queue with a service level;
  • a known-issues note for developers;
  • a decision-rights matrix;
  • a canary pull after each release;
  • seeding the log with this week's churn.
