How TICVAI should handle change

Question (1 October 2026): What is the best way to handle change from now on, whether a table, a UI screen, a missed service or a new requirement? The change should be captured once and pushed only to the affected modules or services. The refresh should become incremental and safe to interrupt. The two channels, ADAM and OpenProject tickets, should be simplified so tickets never drift. In-flight tickets need a rule for when their spec changes. The "audit everything from ingestion to refresh, then re-audit" pass should improve the process rather than only produce findings. Constraints: OpenProject 10 stays, the build starts in 4 days, and the least possible rework.

The recommendation

One rule: OpenProject holds who, when, state and order. The package, served by ADAM at a release tag, holds what. ADAM's existing propose-then-confirm CR flow is the only way a change gets in.

Before Monday 5 October: fences only, nothing new

  1. Run refresh.sh in a throwaway worktree, and swap it into main only when all checks pass. An interrupted run is simply deleted.
  2. Cut tag r1 on the package and the 6 mirrors. ADAM's /ticket records the tag when a ticket is pulled.
  3. Freeze the baseline DDL, with a check that fails if a baseline migration changes. From then on, a table change is a new forward migration.
  4. Pushed keys are frozen. The key-stability check blocks a rename instead of warning.
  5. A one-page developer brief: pull only through ADAM, the OpenProject text is a snapshot, and raise gaps as a CR.

Weeks 1–2

  • One push script. A single idempotent Ruby file: key check, upsert by key, the assignee and week sync, link pruning. Dry run, then apply, on release days only, from a git checkout on the OpenProject server.
  • Pointer ticket bodies, in stages. New tickets first. Unstarted tickets in dry-run batches. A started ticket gets one comment.
  • CR intake. Each CR records its source line, its approver, its triage class (clarification, scope or defect; now or later), the artefact IDs it touches, whether a contract change is breaking or additive, and its effort change. Minutes need client sign-off first. Cut-off is Monday or Thursday noon. The client gets a release note with every drop.
  • Agents on branches. One CR per branch, with the lead reviewing each diff before merging.

Later (week 3 on)

  • Record what each refresh step reads and writes, then scope derives to what a change touches.
  • A reach and cost report for pricing CRs, once the links are proven clean. No client portal.

Audit, then re-audit

  • Group the 293 root issues into classes. Each class becomes a check, or a rule on how CRs are written.
  • The ingestion-to-refresh audit must produce the manifest of what each refresh step reads and writes.
  • The re-audit is every check green, plus 20–30 sampled pulls after each drop. A root issue with no check is not closed.

First thing: before any developer pulls on Monday, run a clean refresh, tag r1 on the package and the 6 mirrors, and make /ticket record that tag on pull.

Where they clashed, and how it was settled

  • Pin or live-with-warning → pin, with the diff visible. ADAM serves the latest release tag, never working HEAD. A ticket keeps the tag it was pulled at. A breaking contract change forces the producer and consumer tickets onto the same tag.
  • Keys derived from the artefact, or immutable IDs → immutable IDs, and those are the keys already pushed. Nothing is re-keyed. A move between modules is a metadata change. A split creates new keys linked to the parent. Artefact IDs become a field on the ticket.

Blind spots caught in peer review

  • Once code exists, schema changes must be forward-only migrations.
  • Pins can differ between the producer and consumer of the same operation. Contract changes need an additive or breaking label and a compatibility gate.
  • The 6 mirrored repos must carry the same tag.
  • Stripping 4,000 descriptions is itself a mass migration, so it is staged.
  • ADAM becomes a single point of failure. The fallback is the tagged mirrors in git.
  • Plan fields (assignee, week) drift when a change shifts effort.
  • Nothing covers intake: who decides, triage, where a change came from, client sign-off, conflicts with the Decisions Register, changes raised by developers, a feedback note to the client, and review of the edits AI agents make.

Full advisor responses

The Contrarian

The fatal flaw is the plan to make a live, interlinked system handle change while it is still changing. ADAM reading the live package is itself a bug: pin a package version and release on a cadence. Incremental refresh is a trap for now, so generate into a temporary tree and swap. Keys are the root cause, so assign an immutable ID once. OpenProject holds the plan, never the spec. The lead pasting Ruby into a shell is a single point of failure. An audit is theatre unless each root issue becomes a check. Nobody faces the volume, and upstream triage has to say "no" or "later".

The First Principles Thinker

Every failure comes from one choice: the ticket holds a copy of the spec. Tickets should point to the spec, not copy it. Keys should come from what is built, not from where it sits in the plan. The refresh should be atomic (build in staging, then swap), not incremental. Pin started tickets to a commit and show the diff, with a weekly release. Turn the 293 root issues into classes, and each class into a check.

The Expansionist

The links and the lineage are an impact engine already. Point them at a change and you get its reach, and they can drive the incremental derive. ADAM is the only home of ticket content. Each client answer could come with its reach and cost already worked out, which turns scope creep into priced change orders. A decision portal for the 577 decisions. Audits that produce gates. A reusable spec-to-delivery compiler.

The Outsider

You copy generated content into a system that can't regenerate it. Stop copying: a permanent ID, a title, an owner, a week and a link to ADAM. Things that look strange from outside: pasting Ruby when you have shell access (put a git checkout on the server instead); a one-field change costing an hour-long rebuild (nothing records which outputs depend on which inputs); 400 tickets per developer; 9,976 findings that nobody will act on.

The Executor

Don't build anything new before Monday; put fences around what you have. Ticket bodies become pointers, and the sync script becomes the only thing that touches existing tickets. The push becomes one idempotent paste, run twice a week. The refresh runs in a throwaway worktree. CRs list their artefact IDs and ship on Tuesday and Friday. Stamp the commit SHA when a ticket is pulled and show "spec changed" with the diff. Re-pull 20 sampled tickets after each drop. Monday: stamp the SHA and make ticket bodies pointers.

Peer review highlights

What the reviewers said
  • Four of five reviewers rated the Executor strongest: it fits the 4 days, reuses what exists, and names a Monday action. One rated the First Principles Thinker strongest, for its root cause and its keys.
  • All five named the Expansionist as the biggest blind spot: it ignores the constraints, and it trusts a link graph that had 646 stale links this week.
  • What they missed: forward-only migrations; mixed pins; mirrors; ADAM as a single point of failure; mass-migration risk; intake and who decides; changes raised by developers; the feedback loop to the client; review of AI edits; plan fields drifting with effort.
