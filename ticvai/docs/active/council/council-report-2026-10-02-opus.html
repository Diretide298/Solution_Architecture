Council verdict (Opus): a complete audit, and a change log that prevents repeats

"I feel let's do a complete audit, not just for Block A. Then, for any changes ahead, we write a log and instructions, so we can avoid them going forward and have a better way to integrate them." (Chinmay, 2 October 2026; re-run on Opus after the limits were reset)

The one thing to do first

When r2 lands, record its counts in checks/baseline.json. Make check-binding-ratchet a merge gate before any audit fix merges. From then on, every finding becomes a permanent check rather than a repeat.

The recommendation

Today and this weekend

  • Apply r2 to OpenProject. It becomes the baseline, and every fix goes into a later tag.
  • Fix in Friday's release, before any Block A ticket starts:
    • the storefront theme read before sign-in;
    • the guest policy read;
    • staff fields on guest screens.
  • Write the checks:
    • binding ratchet on the 5,613 / 55 / 42 counts, with an allowlist whose entries expire after 14 days;
    • audience match;
    • pre-sign-in session;
    • subject (acting on the caller or on a named customer);
    • change log.
  • Re-audit the Sprint 1–2 Block A tickets (F8).
  • Run the process agents on the Block A apps first, each in its own worktree with checkpoint commits.
  • Budget the AI capacity: A 50%, B 25%, C and D 15%, discovery 10%.
  • Publish the Sprint 1 pull list.

Monday

  • Developers pull from that list.
  • ADAM gets a "spec defect" change-request type that names the broken invariant, so the 12 developers become auditors.

Complete audit, block by block

  • A: F8 on all 659 tickets, plus process agents on the guest web, guest app, POS and kitchen display.
  • B: all checks, plus a simulated pull of one ticket per root class per app.
  • C and D: checks and process agents now; a ticket-level audit once they are broken into tasks.
  • Everywhere:
    • trace the 1,119 MoM inputs and 53 open questions;
    • check that command centres, dashboards and simulation are complete;
    • close the 435 tracker rows.

Change log: ticvai/changes/CHANGELOG.yaml

  • Fields:
    • id, date, source and kind;
    • keys touched and root class;
    • tickets, marked started or unstarted;
    • release tag;
    • client sign-off (required when the change comes from a MoM);
    • prevention: a check, a generator rule, a template field, or none:<reason>;
    • status.
  • An entry closes only when its prevention is merged and fails on the commit before the fix. check-changelog blocks any spec merge that has no CHG id.

How changes reach tickets

  • Unstarted: the ticket picks up the fix at the next tag, through its pointer body.
  • Started: never rewritten. The change request creates a linked delta ticket, and ADAM keeps serving the developer's starting tag until they finish.

Decision churn

  • A plan change is a CHG entry of kind "plan".
  • It changes only at a Tue/Fri release, after 24 hours of cooling off.
  • MoM sign-offs are batched weekly.

Blind spots caught in review

  • The 5,613 count needs classifying, because much of it is static text, so it needs an allowlist whose entries expire.
  • No weekly AI budget.
  • No tag or worktree named for the agents' output.
  • No contract tests on the developers' code.
  • Completeness of command centres, dashboards and simulation.
  • Two screen counts that disagree: 2,447 and 2,422.
The Contrarian

An audit can't finish before Block A starts; it schedules churn instead of stopping it. The backlog already outruns one lead. The generator's counts should be merge gates. r2 pushes known defects into Block A, so only tickets that fully resolve should be pullable. Freeze plan decisions at releases.

The First Principles Thinker

The real question is not "a complete audit". It is that the rules are missing, at 34 findings per root cause. The counts are failing checks. Declare and check audience, need for a session, and subject. Build a ratchet, not a sweep. The log is the history of commits that added checks. Plan decisions belong in a fixed weekly slot.

The Expansionist

Build a catalogue of invariants, where each one becomes a check that runs forever. The 12 developers become auditors through a "spec defect" change request. The change log is the client's sign-off surface. Simulate-before-live is the same discipline, so it can be a product feature.

The Outsider

The specification is still being written, not finished with defects. One person is at the centre of everything. The developers are the cheapest auditors. The jargon blocks newcomers. The screen counts disagree. First: are the Sprint 1 tickets buildable?

The Executor

Clean the tree today. Ratchet checks and a change-log template with a required check ID this weekend. On Monday, developers pull at r2, and AI goes to the A re-audit, then the process agents on the Block A apps, then B. Fix the theme and policy reads before Monday. Plan changes only on Tuesday.

Peer review

Both reviews ranked the Executor's response strongest: it is sequenced, enforceable and fits one lead. They said to add First Principles' typed properties and to move the timing forward now that capacity is reset. They flagged the Contrarian's gate as the biggest blind spot, because it would leave developers idle. Three of the five reviews could not run: the 7 process agents had used up the limit on concurrent agents.
