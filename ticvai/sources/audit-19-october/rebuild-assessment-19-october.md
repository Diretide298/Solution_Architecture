# TICVAI: should we rebuild, and how should Block A be re-planned? (19 October 2026)

Inputs: the client meeting of 19 October (Module-Timelines, Muhamed Allam and Qossai Alqawasmi), the package at r7, the plan
(`handoff/service-docs/plan-tasks.csv`), the screens' wireframe records, PMS statuses, the CR analysis
(`audit-miss-analysis.md`), the 30-ticket pilot (`pilot-dryrun/`) and the stopped Sprint 1 and 2 dry runs (488 tickets walked).

## What the client asked for (19 October)
- Ticketing core first, and inside it the back-office configuration first: products, then events and performances, seat
  assignment, pricing, promotions and bundles, resources, then F&B and retail inventory. Access control and admin are core.
  Finance, then CRM and marketing come after.
- Each configuration area frozen on a dated plan: wireframe sent, client feedback within a day, finalised with a one-day
  buffer. One connected back-office wireframe that grows area by area, not separate ones.
- POS and guest web wireframes are seen and fine; back-end configuration is the gap ("many things which doesn't make sense").
- Once the base configuration exists, the front end runs in parallel and the client tests configuration plus front end.
- Phase 1 go-live in January. A plan e-mail with dates per module is expected.

## 2. How the work is assigned
- Sprints 1 and 2 span **36 modules**. Each developer holds tasks in **18 to 28 modules** (Hrushikant 9, as the database
  owner). Nothing completes as a module a person can test end to end.
- The client's core is thin: Pricing & Promotions 5 tasks, Resources & Capacity 6, Retail 7, Seating & Maps 26; against
  White Label 85, AI 39, Marketing and CRM 47, Finance 38.
- Cause: the plan was sliced by platform and spread breadth-first across all modules to fill each sprint.

## 3. How much of the package is buildable
- Developers raised 100 CRs; 12% were known and released anyway, 55% got past checks that were too narrow or missing, 13%
  we introduced, 16% need decisions (`audit-miss-analysis.md`).
- The dry run walked 488 Sprint 1 and 2 tickets before it was stopped: **2,548 draft gaps, 415 tickets (85%) not buildable
  as written**. Not yet challenged; the pilot kept about 3 in 4 drafts and found 25 of 27 real CRs.
- By kind: contradictions 29%, rules promised but undefined 23%, screen promises with no API 12%, missing routes 8%,
  missing fields 10%, decisions 7%. The same few causes repeat on almost every ticket.
- Root causes: one fact written in several places that drift; prose promises never turned into rules; layers generated
  separately and never walked end to end; screens generated by us (995) or missing (1,299) before the client agreed them;
  the back office generated from one very large input (about 4,000 items), where the model cut corners.

## 4. Recommendation: rebuild module by module, not from scratch
**Worth it: yes, for the back-office configuration and everything that hangs off it. Not for what is stable.**

Keep as is:
- Foundation (hosts, kernel, id, CI, observability), identity basics, the migration infrastructure and the delivered
  migrations (changes become forward migrations), guest web, guest app, the verified POS screens.
- The tooling: ADAM, the release tools, the checks, the dry run.

Rebuild, in the client's order, one module at a time (products, events and performances, seat assignment, pricing,
promotions and bundles, resources, F&B and retail inventory, then finance, then CRM and marketing):
1. **Inputs:** that module's workshop slides, matrix rows and meeting decisions only (meeting notes win over the sheet).
2. **Wireframe:** added to the one back-office wireframe in a small batch; sent to the client; feedback in a day; signed off.
3. **Spec from the signed wireframe:** each screen field traced to its operation, field, column and event, one source of
   truth per fact; every promise a rule, a field, an error or a listed decision.
4. **Gate:** the end-to-end dry run on the module's tickets; no blocking finding left before developers get them.
5. **Tickets as a testable slice:** database, backend and frontend for the module together, owned by a small group,
   ending in a human test: configure it in the back office, see it in POS or guest web.

Developers work on one or two modules at a time. While module N is built, module N+1 is in wireframe and feedback.

## 5. What happens to work already done
- Not wasted: delivered migrations, foundation, identity and guest web/app work stay.
- Sprint 1 and 2 back-office frontend tickets without verified screens should not be started until their module's
  wireframe is signed; they are re-planned into the module slices.
- The dry-run log (2,548 drafts on 488 tickets) is kept as each module's checklist when it is rebuilt.

## Decisions for the lead
1. Adopt module-by-module rebuild in the client's order (recommended), or keep the current plan.
2. Hold new back-office frontend work without a verified wireframe now.
3. Send the client the dated plan e-mail per module (draft on request).
