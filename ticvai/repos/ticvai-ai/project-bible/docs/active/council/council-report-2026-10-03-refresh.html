QUESTION (Chinmay, 3 Oct 2026, 23:00): "Can we optimise the main refresh? Parallel runs or something?"

CONTEXT: TICVAI is a spec package in git (contracts, screens, flows, tables, plan; ~30k files incl. 6 generated repo mirrors). Every release runs tools/refresh-safe.sh: it copies the tree into a throwaway git worktree, runs tools/refresh.sh (65 derive/generate steps, strictly sequential, ~48 min), then runs 54 checkers through tools/run-checks.py (strictly sequential; per-check times sum to ~33 min: check-screens 681 s, check-wireframes 279 s, check-flows 86 s, check-lineage 77 s, audit-links 68 s, check-flow-briefs 61 s, the rest under 60 s; check-package ~630 s already runs alongside), judges the results against a baseline file and merges the derived output into main only on PASS. Total ~80 min per real run. Python 3.9 on Windows (Git Bash); the machine has 32 logical cores but is shared with up to 5-8 Claude agents running in parallel; today one refresh died silently at step 37 under that load (the same step passed alone). Assets that exist: handoff/refresh-manifest.json traces what files each refresh step reads and writes (built by tools/refresh-manifest.py from a traced run); refresh-safe.sh has a --since REF scoped mode (regenerates only steps whose inputs changed since REF); a rule "derive before check" (a root edit cascades to derived files and mirrors). Today the full refresh ran ~6 times (~8 h total); each failure costs another full run. Releases happen several times a week (Tue/Fri plus change requests); Sprint 1 of a 13-sprint build starts Monday. Stakes: refresh time is now the bottleneck of the release loop; but the refresh is also the safety gate (nothing reaches developers unless it passes), so speed must not weaken correctness.
DECISION: how to cut the refresh time, e.g. parallelise steps using the manifest DAG, parallelise run-checks, scoped --since runs, caching, splitting checks into fast/slow tiers, or something else, and in what order, without weakening the gate.

RESPONSES (anonymized):
Response A: The scariest detail is a safety gate that died silently at step 37. Fix loud failure first (exit code + log line per step); stop running the gate on a machine shared with 5-8 agents. The real number is 8 h not 80 min: the release gate is being used as the edit-fix-retry loop; iterate with --since and the specific failing checker, run the full gate once at release. Resume from the failed step instead of step 1. Profile check-screens (11 of 33 min) before building a DAG. Then parallelise checkers if verified read-only (33 -> ~11 min). Be careful with --since/manifest DAG: from one traced run, input-dependent reads are wrong and the gate passes something unchecked. Don't rebuild the release pipeline this weekend.
Response B: Aim higher than parallel. The manifest is most of a build system: content-addressed step cache (hash declared inputs + step script; unchanged -> restore outputs): typical release reruns 5-10 steps, 80 min -> 3-8 min, still a full gate; a run dying at step 37 resumes there. Same for checks: cache per screen by input hash, shard changed screens (recovers ~15 min). Adjacent opportunity: the graph gives automatic impact analysis for every CR (blast radius: derived files, screens, mirrors, tickets) for ADAM's CR costing; clients pay for that. Changes cadence: CRs ship when ready, daily drops. Agents run a scoped cached gate before handoff. Order: cache, sharded checks, DAG parallel capped ~6 workers, impact graph in ADAM.
Response C: The question assumes 80 min is the problem; it's running it 6 times, and parallelism adds failure modes faster than it removes minutes. The silent death is the real bug; parallel load makes it worse (timeouts, memory, Windows file locks, antivirus, git index.lock). Does the gate always catch a silent death, or can truncated output slip to PASS? The manifest DAG from a single traced run misses conditional reads, globs, env-var config, two steps writing one file: races that pass most of the time; --since has the same hole. Don't trust either until sequential vs parallel/scoped outputs are byte-identical several times. Baseline comparison may be ordering-dependent: false FAILs cost a full rerun. Profile check-screens. Don't rebuild the gate this weekend; Sprint 1 Monday.
Response D: Wrong question: 8 hours is paying 80 min six times. It's a non-incremental build system. 1) Fail loud and resume: check each step's exit code and expected outputs; record completed steps; rerun starts at the failed step. 2) Cache by content hash (inputs per manifest + script hash) for steps and checkers; a hash trusts nothing, unlike --since's git diff; gate stays full, most steps finish in ms. 3) Guard missed reads: rebuild the manifest when any tool changes; cold uncached refresh at each Tue/Fri release, diffed against the cached run. 4) Profile check-screens and check-wireframes (16 of 33 min). 5) Parallelise last, cap 3-4 workers.
Response E: The biggest waste was six full runs, one dying silently: fix the cost of a failure first. Monday: 1) refresh.sh fails loudly and resumes (~1 h): set -euo pipefail, timestamped per-step log with exit code, per-step stderr files, --keep-worktree and --from-step N; per-step timings for free. 2) Parallel run-checks, pool of 4 (~2 h): checks read only; per-check output files; sort results before the baseline compare; prove once (sequential vs parallel verdicts identical). 33 min -> ~11-12. 3) Profile check-screens (~half day) to ~120 s -> checks ~5 min. 4) Policy: --since for iteration, full run for the Tue/Fri gate. Not this week: DAG-parallel refresh.sh (manifest from one traced run -> races under load). Expected ~80 -> ~55 min by Wednesday; failures cost minutes.
