# Service documentation and task sheet: plan (23 September)

Decided with Chinmay on 23 September:
- **Audience: both.** A detailed version for developers and a client summary, generated from the same source.
- **Services are built as a slice, then extended.**
- **Format: Markdown + Excel.**

## Scope fact the plan rests on
The four platforms (POS P04, Guest Web P01, Guest Mobile P02, White Labelling P13+P09) call
**340 of about 2,080 operations** across **15 of 17 services**. CrossRegion is untouched; Platform is reached only through White Labelling.

| | POS | Web | Mobile | White Label |
|---|---:|---:|---:|---:|
| Screens | 30 | 46 | 71 | 23 |
| Operations | 140 | 154 | 154 | 88 |

## Service rule: slice, freeze, extend additively
- **Slice** = the operations these four platforms call, plus the Back Office (P08) and Admin (P09) setup operations
  they depend on. POS cannot open without products, prices and tills configured.
- **Finished** = the slice is complete and the contract moves to `1.0.0`.
  - Already at 1.0.0: identity, tenancy, shift, payments.
  - Still at 0.1.0: orders, catalogue, fnb, white-label, marketing-crm.
- **Additive changes after 1.0.0 are a minor bump:** a new operation, a new optional field, or a new table (a new migration).
- **Breaking changes need 2.0.0 plus a deprecation window.** That covers renaming or removing a field, or making an optional field required.
  A gate should enforce this; none exists yet.

## Deliverables (all generated by one script, never hand-edited)
1. **Architecture overview.**
   - Shows the frontend apps, the backend services and the data they sit on.
   - Includes the platform × service matrix.
2. **Frontend.**
   - One section per platform, with an entry for each screen.
   - Each screen entry gives:
     - its purpose and wave
     - its loading, empty, error and offline states
     - the operations it calls, with the service that owns each one and the permission it needs.
3. **Backend.** One section per service, covering:
   - its responsibility, scale and failure mode
   - the tables it owns
   - every in-slice operation: method, path, permission, request and response fields, errors, config scope
   - the services it reads from
   - the screens that call each operation.
4. **Client summary.** Plain language, with no field-level detail.
5. **Task sheet.**
   - One task per service operation group, and one task per screen.
   - A screen task depends on the service tasks behind the operations it calls.
   - Each task records its wave.
   - Output is an **OpenProject import CSV**. OpenProject stays the only plan (CF-124), so this sheet is its input, not a second plan.

## Built (23 September)

| Step | Tool | Output |

| 1. Slice | `tools/derive-delivery-slice.py` | `handoff/delivery-slice.json`: 340 core + 96 setup = 436 operations |
| 2. Developer docs | `tools/build-service-docs.py` | `handoff/service-docs/`: README (architecture), `frontend/*.md` (170 screens), `backend/*.md` (16 services, 11,827 fields) |
| 3. Client summary | the same tool | `client-summary.md` and `TICVAI_First_Release_Client.xlsx`, copied to the repo root as `TICVAI - First Release Summary.*` |
| 4. Task sheet | the same tool | `tasks.csv` and the Tasks sheet: 340 work packages, with 16 service epics → tag-group features and 4 platform epics → 170 screen tasks. Setup is covered by 40 setup-screen tasks (the fewest screens that host every setup operation) |
| 5. Additive gate | `tools/check-contract-compat.py` | Gating, in `run-checks.py`. Passes until something is frozen; `--freeze <contract>` records a baseline in `contracts/frozen/` |

Both generators are in `refresh.sh`. Gaps found are logged as L1–L6 in the action register.

**Nothing is frozen yet.** Freezing is the decision that a service is built. Run `--freeze` when the first service is delivered, not before.
